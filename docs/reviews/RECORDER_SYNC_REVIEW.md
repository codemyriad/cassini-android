## Fixed Findings

### F1 — Active `open_fw` `GETS` stream not cancelled after recovered or failed downloads (High)
- **Status**: Fixed in commit `d33d7924`
- **Files**: [XrecClient.kt](../../core/src/main/kotlin/io/codemyriad/cassini/core/recorder/XrecClient.kt), [XrecClientScriptedTest.kt](../../core/src/test/kotlin/io/codemyriad/cassini/core/recorder/XrecClientScriptedTest.kt)
- **Evidence**:
  - In `/home/silvio/dev/voice-recorder-hw-bt-usb-r2/open_fw/src/xrec_proto.c` (`xrec_poll`, lines 875–944; `handle_ping`, lines 513–529; `handle_stat`, lines 664–681) and `bt_xrec_bluedroid.c` (`BT_XREC_TX_RING = 2048`, `drain_events` called before `xrec_poll`), `open_fw` streams a 64 KiB `GETS` window incrementally as space opens in its 2048-byte TX ring (`~3` 652-byte frames in flight).
  - Crucially, `PING` and `STAT` **do not** clear `ctx->gets_active`; only `LS`, `PUT`, or a new `GETS` reset `ctx->gets_active` (`xrec_proto.c:760`).
  - Commit `2dc20c59` added `resync()` (`PING` + `drainQuiet` until quiet) after `hadRetries` in `XrecClient.download`, assuming all frames of a retried 64 KiB window were already buffered on the wire. On real `open_fw`, if the final retry of a file recovered early (e.g. a shorter fallback window finished the file while an earlier 64 KiB `GETS` or remaining tail was still active on the device), `xrec_poll` kept pumping `XREC` binary frames every time the host drained bytes, causing `resync()` to time out after `RESYNC_ATTEMPTS` and discard a completed download.
  - Worse, when a download exhausted `maxRetries` (`INTEGRITY` / `TIMEOUT`), `XrecClient.download` threw `XrecException` **without** cancelling `ctx->gets_active` or draining the input. `RecorderSync` catches non-link `XrecException`s in `headOnRecorder` and `downloadFailed` and proceeds to the next file on the **same** session; when the next file started at offset `0`, `readWindow` accepted queued offset-`0` frames from the *previous* file whose CRC16 was valid, silently corrupting the second file's audio or 4 KiB SHA-256 header check.
- **Fix**: Added `stopGets(name, size)` in `XrecClient` to issue a 1-byte `GETS` at `offset = size` (which immediately replaces `ctx->gets_active`, emits at most one 0-byte EOF frame, and sets `ctx->gets_active = false` in `xrec_proto.c:914-922`) before calling `resync()` both after `hadRetries` and before throwing `INTEGRITY`/`TIMEOUT` after `failures > maxRetries`.
- **Verification**: `XrecClientScriptedTest.aRecoveredDownloadCancelsAnActiveOpenFwGetsStreamBeforeResyncing` and `XrecClientScriptedTest.aFailedDownloadStopsGetsAndResyncsSoTheNextFileIsNotCorrupted` (verified failing first, then passing).

### F2 — Unreadable suspect header failed open and uploaded the old note's transcript to an unverified recording (High)
- **Status**: Fixed in commit `a0388159`
- **Files**: [RecorderSync.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/RecorderSync.kt), [RecorderSyncTest.kt](../../app/src/test/java/io/codemyriad/cassini/recorder/RecorderSyncTest.kt)
- **Evidence**:
  - When an imported recording's `.cwx` sidecar is missing on the card and a transcript is ready (or was previously uploaded), `SyncPlanner.suspects` flags it so `RecorderSync.verifySuspects` compares its first 4 KiB SHA-256 before trusting `(name, size)`.
  - In `RecorderSync.verifySuspects` (`2dc20c59`, lines 452–462), `headOnRecorder` returned `null` on any non-link `XrecException` (such as a transient `ERR,SDIO`), and `verifySuspects` filtered with `head != null && head != suspect.headSha256`.
  - When `head == null`, the old record remained in `RecorderDeviceState.recordings` **and** `SyncPlanner.plan` immediately scheduled `PlannedUpload` for it in the very same sync. `RecorderSync` then uploaded the old note's `.cwx` sidecar onto the unverified `.wav`. Once that `.cwx` landed on the card, `SyncPlanner.suspects` (`listing.none { it.name.equals(sidecar, true) }`) never checked the file again—attaching the wrong transcript on the recorder and permanently preventing the new post-wipe recording from being imported.
- **Fix**: `verifySuspects` now returns the case-folded names of suspects whose header read returned `null`, and both `syncWith` (`SyncMode.UPLOADS`) and `latestUploads` (`SyncMode.FULL`) exclude those recordings from `uploads` so no sidecar is written until a later sync reads and verifies their 4 KiB header.
- **Verification**: `RecorderSyncTest.anUnreadableSuspectGetsNoOldTranscriptAndIsCheckedAgainLater` (verified failing first, then passing).

### F3 — `GraphRecorderLibrary` skipped `refreshIfStale` and emitted 0-word transcripts when Room word cache was evicted (High)
- **Status**: Fixed in commit `67390dd2`
- **Files**: [GraphRecorderLibrary.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/GraphRecorderLibrary.kt), [GraphRecorderLibraryTest.kt](../../app/src/test/java/io/codemyriad/cassini/recorder/GraphRecorderLibraryTest.kt)
- **Evidence**:
  - Cassini's `document.opus` is authoritative while Room's `words` table is a rebuildable cache (`CacheDao.dropWords` / `incompleteVariantsBlocking`). `NoteViewModel`, `NoteRepository.selectVariant`, and `DocumentRepository` call `refreshIfStale(noteId)` before reading `words`.
  - `GraphRecorderLibrary.transcript` (`2dc20c59`, lines 52–68) checked `finished.wordCount > 0` on `VariantEntity` and then read `notes.words(noteId, finished.variantId)` **without** calling `notes.refreshIfStale(noteId)`. Whenever `words` rows had been evicted or were stale, `notes.words` returned `emptyList()`, producing a 0-word `CwxTranscript` whose hash differed from the previously uploaded version and **overwrote** the valid `.cwx` transcript on the recorder with an empty one.
  - Additionally, `GraphRecorderLibrary.transcript` resolved `selectedVariant ?: isDefault` *before* filtering `it.readable && it.wordCount > 0` and omitted the `firstOrNull()` fallback used by `NoteRepository.selectedVariant`.
- **Fix**: Call `notes.refreshIfStale(noteId)` for live `DOCUMENT` notes before reading variants/words, filter `details.variants.filter { it.readable && it.wordCount > 0 }` prior to `selectedVariant ?: isDefault ?: firstOrNull()`, and return `null` if `words` is still empty.
- **Verification**: `GraphRecorderLibraryTest.transcriptsRefreshDroppedWordCacheAndFallBackToAReadableVariant` (verified failing first, then passing).

### F4 — `RecorderSyncService` skipped `startForeground` on re-entry, lingered 10 s after fast runs, and `attempt()` started the service on `Busy` (High)
- **Status**: Fixed in commit `ab8583de`
- **Files**: [RecorderSyncService.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/RecorderSyncService.kt), [RecorderRunner.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/RecorderRunner.kt), [RecorderSync.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/RecorderSync.kt), [AppGraph.kt](../../app/src/main/java/io/codemyriad/cassini/AppGraph.kt), [RecorderSyncServiceTest.kt](../../app/src/test/java/io/codemyriad/cassini/recorder/RecorderSyncServiceTest.kt), [RecorderTranscriptPushTest.kt](../../app/src/test/java/io/codemyriad/cassini/recorder/RecorderTranscriptPushTest.kt)
- **Evidence**:
  1. **Process crash on Android 8–16**: `RecorderSyncService.onStartCommand` (`2dc20c59`, lines 49–55) guarded `enterForeground(...)` with `if (!foreground)`. In Android's `ActiveServices.startServiceLocked`, **every** `ContextCompat.startForegroundService` call sets `r.fgRequired = true` even when the service is already in the foreground. Any second `startForegroundService` while `RecorderSyncService` was alive (e.g. tapping "Sync now" during a background upload push, or a new sync starting during `follow()`'s 500 ms post throttle) skipped `startForeground()` and triggered `ForegroundServiceDidNotStartInTimeException`. (Compare `ProcessingService.onStartCommand`, which calls `enterForeground` on every delivery.)
  2. **10-second stuck notification**: `RecorderRunner.syncNow()` called `service.start()` before `sync.sync()`. When `sync.sync()` finished quickly (`Unreachable`, `RebindNeeded`, `Busy`) before `follow()` ran on the main looper, `sync.activity` was already `Idle` and `withTimeoutOrNull(START_GRACE_MS)` kept the `"Syncing with the recorder"` foreground notification visible for 10 seconds.
  3. **Spurious `startForegroundService` on `Busy`**: `RecorderRunner.attempt()` launched `holder` watching shared `sync.activity` *before* acquiring `RecorderSync`'s lock, so an `attempt(UPLOADS)` returning `SyncOutcome.Busy` while another sync was downloading could still invoke `service.start()`.
- **Fix**: Call `enterForeground` unconditionally on every `onStartCommand`; track active service-backed runs in `RecorderRunner.serviceActive` so `RecorderSyncService.follow()` exits immediately when no service run is pending and wakes immediately when `sync.activity` returns to `Idle`; and trigger `attempt()`'s service start via `RecorderSync.sync(..., onMovingFiles)` only after that run owns the sync lock and moves files. (Also fixed a test-side `seen = waits.size` race in `RecorderTranscriptPushTest.waitsUpTo`.)
- **Verification**: `RecorderSyncServiceTest` (3 tests, verified failing first, then passing).

### F5 — `StreamXrecInput.close()` leaked its pump thread when full and failed to wake blocked readers (Medium)
- **Status**: Fixed in commit `5320e56e`
- **Files**: [XrecInput.kt](../../core/src/main/kotlin/io/codemyriad/cassini/core/recorder/XrecInput.kt), [BluetoothRecorderRadio.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/BluetoothRecorderRadio.kt), [XrecPrimitivesTest.kt](../../core/src/test/kotlin/io/codemyriad/cassini/core/recorder/XrecPrimitivesTest.kt)
- **Evidence**:
  - In `StreamXrecInput` (`2dc20c59`, lines 60–116), `close()` closed the underlying `InputStream` and joined the pump thread for up to 1 s **without** setting a `closed` flag or calling `lock.notifyAll()`.
  - If the 128 KiB ring buffer was full when `close()` was called (e.g. watchdog abort or cancellation while `open_fw` streamed a 64 KiB window), the pump thread was parked in `while (available == buffer.size) lock.wait()`—not in `source.read()`—so `source.close()` never woke it, `close()` stalled for `JOIN_MILLIS` (`1_000 ms`), and the `"recorder-link"` thread leaked permanently for the lifetime of the app process.
  - Conversely, if a reader thread was blocked in `read()`'s `lock.wait(remaining)` while `source.read()` on a `BluetoothSocket` ignored close until RFCOMM teardown, closing `StreamXrecInput` left the reader stuck until the multi-second read timeout expired. `BluetoothRecorderRadio.SocketLink.close()` also closed `socket` before `stream.close()`.
- **Fix**: Added a `closed` state inside `StreamXrecInput`'s monitor, signalled `lock.notifyAll()` before `source.close()`, woke both `awaitSpace` and `read` immediately on `closed`, and closed `stream` first in `SocketLink.close()`.
- **Verification**: `XrecPrimitivesTest.closingAFullStreamXrecInputEndsItsPumpThread` and `XrecPrimitivesTest.closingStreamXrecInputWakesABlockedReaderAtOnce` (verified failing first, then passing).

### F6 — Case-sensitive `.wav` matching on case-insensitive `/record` and `XrecNames.isSidecarName` mismatch with firmware (Medium)
- **Status**: Fixed in commit `a977eac7`
- **Files**: [XrecProtocol.kt](../../core/src/main/kotlin/io/codemyriad/cassini/core/recorder/XrecProtocol.kt), [SyncPlanner.kt](../../app-logic/src/main/kotlin/io/codemyriad/cassini/recorder/SyncPlanner.kt), [RecorderSync.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/RecorderSync.kt), [XrecProtocolTest.kt](../../core/src/test/kotlin/io/codemyriad/cassini/core/recorder/XrecProtocolTest.kt), [SyncPlannerTest.kt](../../app-logic/src/test/kotlin/io/codemyriad/cassini/recorder/SyncPlannerTest.kt), [RecorderSyncTest.kt](../../app/src/test/java/io/codemyriad/cassini/recorder/RecorderSyncTest.kt)
- **Evidence**:
  - In `open_fw/src/xrec_proto.c` (`is_rec_sidecar_name`, lines 243–257) and `XREC_PROTOCOL.md` §6.1, valid `REC,<name>` targets must not start with `.`, must have `len > 4`, and match `.cwx` case-insensitively (`str_eq_ci`). `XrecNames.isSidecarName` checked only `isPutName(name) && name.endsWith(".cwx")`, accepting `".cwx"` and `".wav.cwx"` (so `sidecarFor(".wav")` returned `".wav.cwx"` instead of `null`) while rejecting `"REC_0001.CWX"`.
  - On the recorder's exFAT `/record` volume, filenames are ASCII case-insensitive (`FakeRecorder` and `xrec_proto.c` both use case-insensitive lookup). `SyncPlanner` matched `.cwx` case-insensitively, but `SyncPlanner` (`known`, `listing.has`, `partial`) and `RecorderSync` (`markAbsent`, `withRecording`, `checked`, `unverified`) matched `.wav` names with case-sensitive `==`. Case changes over USB caused duplicate RFCOMM downloads and false `absent` marks, and post-wipe replacement of `REC_0001.WAV` by `rec_0001.wav` left two `StoredRecording` entries in `recorder.json` targeting the same `REC_0001.cwx` sidecar.
- **Fix**: Aligned `XrecNames.isSidecarName` with `is_rec_sidecar_name` (`!name.startsWith('.') && name.length > SIDECAR_EXTENSION.length && isSidecar(name)`) and normalized recording filename keys with `Locale.ROOT` case-insensitivity across `SyncPlanner` and `RecorderSync` (including renaming a resumed `.part` file if its listing case changed).
- **Verification**: `XrecProtocolTest`, `SyncPlannerTest.aRecordingInAnotherCaseIsTheSameFile`, and `RecorderSyncTest.recordingsOnTheCardAreMatchedWithoutCase` (verified failing first, then passing).

### F7 — `RecorderSync` lock handoff and `awaitIdle()` concurrency races (Medium)
- **Status**: Fixed in commit `836eadf1`
- **Files**: [RecorderSync.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/RecorderSync.kt), [RecorderSyncTest.kt](../../app/src/test/java/io/codemyriad/cassini/recorder/RecorderSyncTest.kt)
- **Evidence**:
  - In `RecorderSync.sync` and `bind` (`2dc20c59`, lines 212–232, 279–296), `running = null` and `held.value = false` executed **before** `lock.unlock()`.
  - Any caller resumed from `awaitIdle()` (`held.first { !it }`, notably `RecorderTranscriptPush` after seeing `SyncOutcome.Busy`) could immediately invoke `sync(SyncMode.UPLOADS)` while `lock` was still locked on the releasing coroutine, receiving a spurious `SyncOutcome.Busy` and spinning or missing the push window.
  - Similarly, a `sync(SyncMode.FULL)` arriving between `running = null` and `lock.unlock()` (or between `lock.tryLock()` and `running = mode`) saw `!lock.tryLock()` with `running == null` and falsely returned `SyncOutcome.Busy` instead of waiting behind `UPLOADS`. Conversely, multiple `FULL` syncs arriving during `UPLOADS` queued unboundedly on `lock.lock()`, and `held` briefly pulsed `false` across the `UPLOADS -> FULL` handoff.
- **Fix**: Coordinated `lock.tryLock()`, `running`, at most one `fullQueued` waiter, `bindWaiters`, and an atomic `active` count (`MutableStateFlow<Int>`) under `stateLock`, unlocking `lock` *before* decrementing `active` to `0` and cleaning up `fullQueued`/`bindWaiters`/`active` if `lock.lock()` is cancelled.
- **Verification**: `RecorderSyncTest.awaitIdleResumesOnlyAfterTheLockIsReleased` and `RecorderSyncTest.atMostOneFullSyncQueuesBehindAnUploadOnlySyncAndAwaitIdleCoversTheHandoff` (verified failing first, then passing).

### F8 — `RecorderCompanion.deviceOf` lost `"Cassini_XX"` device name on API 33–36 and `BluetoothRecorderRadio.bond` failed on bond-state race (Medium)
- **Status**: Fixed in commit `fc5de494`
- **Files**: [RecorderCompanion.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/RecorderCompanion.kt), [BluetoothRecorderRadio.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/BluetoothRecorderRadio.kt), [RecorderAndroidAdaptersTest.kt](../../app/src/test/java/io/codemyriad/cassini/recorder/RecorderAndroidAdaptersTest.kt)
- **Evidence**:
  1. In AOSP Android 13–16 (`API 33–36`), `AssociationInfo.getDisplayName()` is `null` for non-self-managed `BluetoothDeviceFilter` associations. `RecorderCompanion.associationDevice` (`2dc20c59`, lines 91–99) returned `RecorderDevice(address, info.displayName?.toString() ?: "Cassini")` without consulting `info.associatedDevice?.bluetoothDevice` (API 34+), `EXTRA_DEVICE`, or `BluetoothAdapter.getRemoteDevice(address)`, causing every CDM-associated recorder on Android 13+ to lose its `"Cassini_XX"` identifier in the UI and `recorder.json`.
  2. In `BluetoothRecorderRadio.bondStates` (`2dc20c59`, line 108), `if (state != BluetoothDevice.BOND_BONDING && !device.createBond()) trySend(NOT_STARTED)` invoked `device.createBond()` if `device.bondState` reached `BOND_BONDED` between the initial check (line 73) and broadcast-receiver registration (line 106). Android's `AdapterService.createBond()` returns `false` when `bondState != BOND_NONE`, making `bond()` fail with `BondResult.FAILED` (`BindOutcome.NotBonded`) on an already-bonded recorder.
- **Fix**: `RecorderCompanion.associationDevice` now falls back from `info.displayName` to `info.associatedDevice?.bluetoothDevice` (API 34+), `EXTRA_DEVICE`, and `BluetoothAdapter.getRemoteDevice(address)` (guarded by `RecorderPermissions.granted`), and `BluetoothRecorderRadio.bondStates` calls `createBond()` only when `state == BluetoothDevice.BOND_NONE`.
- **Verification**: `RecorderAndroidAdaptersTest.companionResultFallsBackToBluetoothDeviceNameWhenAssociationDisplayNameIsNull` and `RecorderAndroidAdaptersTest.bondSucceedsWhenDeviceBecomesBondedBeforeCreateBondRuns` (verified failing first, then passing).

### F9 — `KeystoreKeyVault.wrap` could not recover from an invalidated Keystore key, and `RecorderSync.forget()` left `.part` audio and wrapping key behind (Medium)
- **Status**: Fixed in commit `0e78281d`
- **Files**: [KeystoreKeyVault.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/KeystoreKeyVault.kt), [RecorderPorts.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/RecorderPorts.kt), [RecorderSync.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/RecorderSync.kt), [RecorderAndroidAdaptersTest.kt](../../app/src/test/java/io/codemyriad/cassini/recorder/RecorderAndroidAdaptersTest.kt), [RecorderSyncTest.kt](../../app/src/test/java/io/codemyriad/cassini/recorder/RecorderSyncTest.kt)
- **Evidence**:
  1. `KeystoreKeyVault.wrap` (`2dc20c59`, lines 18–24, 41–43) called `existingKey() ?: newKey()` and passed it straight to `cipher.init(Cipher.ENCRYPT_MODE, ...)`. If the Android Keystore entry became unrecoverable or invalidated (`UnrecoverableKeyException` / `KeyPermanentlyInvalidatedException`), `unwrap()` threw `GeneralSecurityException` and marked `rebindNeeded = true`, **but re-binding then threw `GeneralSecurityException` inside `wrap()` every time**, leaving recorder sync permanently broken until app storage was cleared.
  2. `RecorderSync.forget()` (`2dc20c59`, lines 299–301) only wrote `binding = null` in `recorder.json`. Any interrupted `.part` audio recording in `cache/recorder/<address>/` (unimported personal audio that no future sync would clean up unless the same MAC was bound again), its `partial` metadata in `RecorderDeviceState`, and the Keystore wrapping key remained on disk, at odds with [PRIVACY.md](../../PRIVACY.md).
- **Fix**: `KeystoreKeyVault.wrap` now catches `GeneralSecurityException` from `existingKey()` / `cipher.init`, deletes the broken Keystore entry via `clear()`, and generates a fresh AES-256-GCM key; `RecorderSync.forget()` clears `partial` on the forgotten device state, invokes `parts.vault.clear()`, and deletes `parts.downloads` (`cache/recorder/`) while keeping the imported-file history in `recordings`.
- **Verification**: `RecorderAndroidAdaptersTest.keystoreVaultRecoversWhenExistingKeyIsUnusable` and `RecorderSyncTest.forgetDeletesCachedPartFilesAndWrappingKeyWhileKeepingImportedRecords` (verified failing first, then passing).

## Not Fixed / By-Design & Informational Findings

### N1 — Untranscribed and rejected recordings skip the 4 KiB header suspect check (Low — Not fixed, documented design trade-off)
- **Files**: [SyncPlanner.kt](../../app-logic/src/main/kotlin/io/codemyriad/cassini/recorder/SyncPlanner.kt), [SyncPlannerTest.kt](../../app-logic/src/test/kotlin/io/codemyriad/cassini/recorder/SyncPlannerTest.kt), [docs/recorder-sync.md](../../docs/recorder-sync.md)
- **Evidence & Reason**: `SyncPlanner.suspects` checks `sendsOrSent` (`transcriptUploadedVersion != null || (version != null && version != transcriptRefusedVersion)`), explicitly tested by `SyncPlannerTest.suspectsAreKnownFilesWithoutTheirSidecar` (`REC_0004.wav`, `"nothing to send"`) and documented in `docs/recorder-sync.md` ("Checking its first 4 KiB before trusting `(name, size)`"). Skipping the `GETS` check when no transcript is ready avoids reading 4 KiB over RFCOMM for every untranscribed recording on every background auto-sync poll. The residual edge case—a card wipe followed by a new recording with the **exact** same byte length and name as an untranscribed (or import-rejected) recording—is benign for transcript integrity (no wrong transcript is uploaded, and as soon as the first note finishes transcription its missing sidecar triggers `suspects` and imports the new recording). Left as designed.

### N2 — `RecorderRows` shows `TRANSCRIBED` ("Waiting for the recorder…") for USB-copied `.wav` files whose stem cannot form a `REC` sidecar (Low — Not fixed, non-recorder filenames only)
- **Files**: [RecorderViewModel.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/RecorderViewModel.kt), [RecorderTexts.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/RecorderTexts.kt), [RecorderRoute.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/RecorderRoute.kt)
- **Evidence & Reason**: `RecorderRows.status` returns `RecordingStatus.TRANSCRIBED` whenever `note.transcribed && transcriptUploadedVersion == null && !stored.absent`, without checking `XrecNames.sidecarFor(stored.recording.name) != null`. Recorder-made files are always `REC_NNNN.wav` (12 ASCII characters), which always have a valid sidecar name (`<= 30` ASCII chars). Only a manually USB-copied `.wav` in `/record` with a non-ASCII or `> 26`-character stem can hit this state (`SyncPlanner` and `pendingUploads` already skip uploading it cleanly without retrying). Left unchanged to avoid adding UI copy/states for files the recorder firmware never creates.

### N3 — Speaker renames and variant switches wait for the next sync rather than triggering `RecorderTranscriptPush` (Low — Not fixed, documented scope)
- **Files**: [RecorderFeature.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/RecorderFeature.kt), [RecorderRunner.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/RecorderRunner.kt), [docs/recorder-sync.md](../../docs/recorder-sync.md)
- **Evidence & Reason**: `RecorderFeature.notes` feeds `RecorderTranscriptPush` a `Set<String>` of note IDs that have a finished transcript, and `RecorderTranscriptPush.follow()` triggers immediately when `ready - previous` is non-empty (plus once at process start via `pendingUploads()`). Renaming a speaker or switching variants on an already-transcribed note keeps the note ID in `ready`, so it is uploaded on the next full/auto sync or next app start (`EncodedTranscript.version` hashes `variantId` + SHA-256 of the CWX bytes). Explicitly documented in `docs/recorder-sync.md` ("Speaker edits and another selected variant go on the next sync").

### N4 — `BluetoothRecorderRadio` uses `RECEIVER_EXPORTED` for `ACTION_BOND_STATE_CHANGED` (Informational — Verified safe)
- **Files**: [BluetoothRecorderRadio.kt](../../app/src/main/java/io/codemyriad/cassini/recorder/BluetoothRecorderRadio.kt)
- **Evidence & Reason**: On Android 14+ (`API 34+`), `BluetoothDevice.ACTION_BOND_STATE_CHANGED` is broadcast by `com.android.bluetooth` (`BLUETOOTH_UID = 1002`), which dynamic `RECEIVER_NOT_EXPORTED` receivers can miss on Android 14 builds where only `SYSTEM_UID` (`1000`) is exempted. `ACTION_BOND_STATE_CHANGED` is declared as a `<protected-broadcast>` in the Android framework manifest, so third-party apps cannot forge it, and `bondStates` filters by `changed?.address == device.address` and unregisters in `awaitClose`.

### N5 — `CwxEncoder` conformance with `open_fw/src/cwx.c` (Informational — Verified conformant)
- **Files**: [CwxEncoder.kt](../../core/src/main/kotlin/io/codemyriad/cassini/core/recorder/CwxEncoder.kt), [CwxEncoderTest.kt](../../core/src/test/kotlin/io/codemyriad/cassini/core/recorder/CwxEncoderTest.kt)
- **Evidence & Reason**: Cross-checked header fields (`CWX1` magic, version `1`, flags `0`, `duration_ms`, speaker/word/string-pool counts and offsets, 64-byte header), speaker record (`label_off`, `label_len <= 255`, `color_rgb24` matching Cassini's speaker palette), word record (`start_ms <= end_ms`, monotonic sort by `(startMs, endMs)`, `speaker_idx` or `0xFF`, `text_off`, `text_len <= 255`), UTF-8 codepoint boundary truncation (never splitting multi-byte sequences), and budget enforcement (`MAX_CWX_BYTES = 307_200`, `MAX_WORDS = 65_535`, `MAX_SPEAKERS = 254`) against `/home/silvio/dev/voice-recorder-hw-bt-usb-r2/open_fw/src/cwx.c` and golden fixtures in `core/src/test/resources/recorder/`.

### N6 — Key material, backup exclusion, and `DocumentsProvider` isolation (Informational — Verified safe)
